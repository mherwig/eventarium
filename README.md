## Components

| Binary | Role | Listens | Spec |
| --- | --- | --- | --- |

Kafka consumer groups: `router` (events-\*), `dispatcher` and `sse-delivery`
(both on `deliveries`, by channel), one `sse-live-<NODE_ID>` per gateway node,
`status-writer`. The presence view joins no group: every gateway node folds the
whole `sse-presence` topic itself, because `pick()` has to know the connections
of *all* nodes and a group would hand each node only its slice of them.

### More than one replica

Every component runs with any number of replicas. Work Kafka splits by
partition (consuming `events-*`, `deliveries`, `delivery-status`, the live
topic) needs no coordination - the group does it. Two pieces of work are *not*
partition-scoped, and both are handled:

- **The inbox duty of the dispatcher** (draining parked rows, sweeping expired
  ones) runs under a PostgreSQL advisory-lock lease, so exactly one dispatcher
  of the fleet does it while the others stay out of the inbox entirely. A
  standby takes over on its next 500 ms tick when the holder dies, and a
  rolling restart hands the lease over on shutdown. Without this, N replicas
  would each `SELECT ... LIMIT` the same parked rows and deliver the backlog N
  times, exactly when a receiver has just recovered. Everything else in the
  dispatcher - parking, counting, acking - is per record and runs on every node.
- **The presence view of the gateway** consumes groupless (above), so each node
  sees the connections of every node instead of its own slice.

Verified live with two dispatchers and two gateways: one lock row in
`pg_locks`, takeover in one tick, both gateways reporting the same `presence`
count while hosting different connections, and 40 parked rows drained to 40
receipts - not 80.

## Storage responsibilities

Neither database is on the delivery hot path: events and delivery payloads
live in Kafka, and both stores are read/written off that path.

| Store | Holds | Why there |
| --- | --- | --- |
| **Kafka** | `events-<class>` (the events themselves), `deliveries` (one record per subscription per event), `delivery-status`, `sse-live`, `sse-presence` | The data plane: buffering, fan-out, ordering per key, at-least-once replay from offsets |
| **PostgreSQL** | `event_types` + `subscriptions` (the registry, §5/§7), `inbox` (parked deliveries, §6.6), `replay_jobs` (replay job metadata, §11) | Small, transactional, mutated: CRUD with constraints, and the inbox needs ordered per-subscription scans, batched deletes and partition drop at expiry |
| **ClickHouse** | `delivery_status`: one append-only row per status transition (`pending → sent → delivered/failed/parked`) with attempt, HTTP code, latency, reason (§9/§10) | High-volume append plus analytical reads (current status via the `(ts, attempt, rank)` latest key, distinct-delivery counts, keyset pagination), cheap expiry via partition TTL — the shape MergeTree is built for |

The status table grows with traffic × fan-out × attempts (~20k rows/s at the
N1 rate), which is why it is not in PostgreSQL; see the load-test section for
the measured numbers. The boundary is cheap to revise: status-writer is the
only writer, status-api the only reader.

## Running locally

### 1. Infrastructure

```sh
docker compose up -d
go run ./cmd/admin all        # topics + PostgreSQL migrations + ClickHouse table
```

`admin` is idempotent; run it again whenever you add a migration or a topic.
Ports: Kafka `9092`, PostgreSQL `5432`, ClickHouse `8123` (HTTP) / `9000`
(native). Both databases use user/password `pubsub`.

### 2. Build

```sh
go build -o bin/ ./cmd/...
```

### 3. Start the services

Each service is standalone; run them in separate terminals or backgrounded
(`setsid nohup ./bin/<name> > /tmp/<name>.log 2>&1 < /dev/null &`, otherwise
they die with your shell). In order:

```sh
./bin/publish-api                        # data plane, :8080
HTTP_ADDR=:8083 ./bin/registry-api       # control plane, :8083
./bin/router                             # health :8085, needs PostgreSQL for the registry
./bin/dispatcher                         # health :8086, needs PostgreSQL for the inbox
./bin/sse-gateway                        # :8082
./bin/status-writer                      # health :8087, needs ClickHouse
./bin/status-api                         # :8081
./bin/replay-api                         # :8084, needs PostgreSQL + ClickHouse + Kafka
```

All of them expose `/healthz` (liveness) and `/readyz` (readiness) without
authentication; the three workers serve only those two. Liveness never fails
because a database is down — restarting a consumer would gain nothing — while
readiness does: it also reports `starting` until the registry, the inbox
partitions and the Kafka client are set up. A restart is safe: Kafka offsets
and the inbox hold the state, and consumers rejoin their groups.

### 4. Register, subscribe, publish, receive

The harness does all of this for you (§5); manually, one event end to end.
Every API call needs a bearer token from `minttoken` (scopes default to
`publish,subscribe,status:read`):

```sh
export JWT_SECRET=dev-secret
T=$(./bin/minttoken -owner team-a -scopes publish,subscribe,status:read)
```

**Register an event type** (control plane, `:8083`). `retention_class` is
`live`, `short`, `day` or `week` and selects the Kafka topic the events land
on. `ordering_key_def` (optional) derives the ordering key for `key_ordered`
subscriptions: `subject`, `ext:<name>`, or `json:<dotted.path>` in the data;
empty falls back to the publisher's partition key:

```sh
curl -s -X POST localhost:8083/v1/event-types -H "Authorization: Bearer $T" \
  -H 'Content-Type: application/json' \
  -d '{"name":"orders.created","retention_class":"short","content_type":"application/json"}'
```

**Create a webhook subscription** with a CEL attribute filter and a
projection (`:8083`):

```sh
curl -s -X POST localhost:8083/v1/subscriptions -H "Authorization: Bearer $T" \
  -H 'Content-Type: application/json' \
  -d '{"event_type":"orders.created","channel":"webhook",
       "callback_url":"http://localhost:9090/hook",
       "filter":"attributes[\"region\"] == \"eu\"",
       "projection":["order_id","total"],
       "delivery_mode":"key_ordered","rate_limit_per_s":100}'
```

`filter` is CEL over `attributes` and `data`; `projection` is the allowlist
of data fields the subscriber receives (§6.2). The callback may be any HTTP
endpoint; the simulated receiver of the harness listens on `:9090/hook`:

```sh
./bin/harness recv -addr :9090 -out recv.jsonl &
```

**Create an SSE subscription** the same way, with `channel: "sse"` (no
callback URL):

```sh
curl -s -X POST localhost:8083/v1/subscriptions -H "Authorization: Bearer $T" \
  -H 'Content-Type: application/json' \
  -d '{"event_type":"orders.created","channel":"sse"}'
```

**Publish an event** (data plane, `:8080`, binary CloudEvents binding —
`ce-*` headers carry the attributes, the body is the data member; use
`Content-Type: application/cloudevents+json` for structured mode, or
`harness pub` for load). `ce-region` becomes the extension attribute
`region` that the filter reads:

```sh
curl -s -X POST localhost:8080/v1/events -H "Authorization: Bearer $T" \
  -H 'Content-Type: application/json' \
  -H 'ce-specversion: 1.0' -H 'ce-id: 42' -H 'ce-source: /orders' \
  -H 'ce-type: orders.created' -H 'ce-region: eu' \
  -d '{"order_id":"o-1","total":99.9,"internal":"secret"}'
```

A `201` means *accepted into the event log*, not *will be delivered* — and an
event type nobody subscribes to would otherwise be accepted silently and
routed to nothing. So when the registry knows **zero** subscriptions for the
event's type, the response carries an extra advisory field (absent otherwise,
so the normal `201` is unchanged):

```json
{"event_ref":"94453d07-...","event_type":"track.empty","retention_class":"short",
 "expires_at":"2026-10-29T22:23:35Z",
 "warning":"no subscription is registered for event type \"track.empty\": the event is accepted and stored, but nothing will be delivered"}
```

It is a warning, never an error: a subscription can be created a second later,
and `422 unknown event type` already rejects the typo case. Note what it does
*not* report — the number of subscriptions. That count would be a **candidate**
count (publish does not evaluate CEL filters), so `"subscriptions": 5` could
still mean zero deliveries; it would read as a delivery forecast. The per-event
answer to "did the filter accept it?" lands in the status store a moment later
as [`filtered`](#delivery-statuses).

The publish API caches the registry, and so do the router, dispatcher and SSE
gateway. Creating an event type or subscription fires a trigger (migration
003) on `event_types`/`subscriptions`, every service LISTENs for it and
reloads as soon as the writing transaction commits — so once the
registry-api call has returned, the type or subscription is usable; no
settling time. `REGISTRY_POLL` (2 s for publish-api) is only the safety net
for notifications missed while a listener was down.

**Receive on the webhook**: the dispatcher POSTs the event — binary binding
by default, with delivery metadata in `pubsub-*` headers (never inside the
event, §5) and an HMAC over the body when `WEBHOOK_SIGNING_SECRET` is set:

```
POST /hook
ce-specversion: 1.0
ce-id: 42
ce-source: /orders
ce-type: orders.created
ce-region: eu
pubsub-delivery-id: <event-ref>/<subscription-id>
pubsub-event-ref: 4f4e...            # the event's identity
pubsub-attempt: 1
pubsub-seq: 7:1904                   # position on the deliveries topic
X-Pubsub-Signature: sha256=...       # only with WEBHOOK_SIGNING_SECRET

{"order_id":"o-1","total":99.9}      # projection applied: "internal" is gone
```

**Receive on the SSE**: connect to `:8082` with a subscribe-scoped token:

```sh
curl -N -H "Authorization: Bearer $T" \
  "http://localhost:8082/sse?subscription_id=<id>&consumer_id=demo"
```

(The spike accepts the token only in the `Authorization` header;
browser `EventSource` cannot send headers, so a real deployment would add a
short-lived token in the query string or a cookie — like the usual
`?access_token=` dance.)

Each delivery is one frame — `id` is the sequence, `data` the delivery
envelope with the full CloudEvent inside:

```
id: 7:1904
event: delivery
data: {"delivery_id":"...","event_ref":"...","sequence":"7:1904",
       "event":{"specversion":"1.0","id":"42","source":"/orders",
                "type":"orders.created","datacontenttype":"application/json",
                "data":{"order_id":"o-1","total":99.9}}}
```

`sent` becomes `delivered` only when the client acknowledges the sequence —
either `POST /sse/ack` with `{"subscription_id":...,"sequence":"7:1904"}`, or
implicitly by receiving an event it then acks. On reconnect, echo the last
received `id` back as a `Last-Event-ID` header (or `?last_event_id=`): the
gateway then replays everything after that cursor straight from the
`deliveries` topic — covering parked rows *and* deliveries that died with the
old connection — merges it with the live stream, and deduplicates. The
`harness sse` subcommand does exactly that: it acks each event, reconnects
automatically with the cursor of the last event it received, deduplicates by
event reference, and logs what it saw:

```sh
./bin/harness sse -sub <id> -owner team-a -addr http://localhost:8082 \
  -out sse.jsonl -duration 60s
# resume a stored cursor explicitly on first connect:
./bin/harness sse -sub <id> -owner team-a -last-event-id 7:1904 ...
```

**Query the outcome** — the delivery's status history and a per-status
summary (`status:read` scope, `:8081`):

```sh
T=$(./bin/minttoken -owner team-a -scopes status:read)

# one row per delivery with its current status (filter: ?status=&from=&to=,
# paging: ?limit=&cursor=)
curl -s localhost:8081/v1/subscriptions/<id>/deliveries -H "Authorization: Bearer $T"

# counts per status + total, over the last 24 h (narrow with ?since=RFC3339)
curl -s localhost:8081/v1/subscriptions/<id>/status-summary -H "Authorization: Bearer $T"
# → {"counts":{"delivered":40,...},"total":40}
```

**Delivery statuses** — every transition is one append-only row in
ClickHouse; the complete list of the eleven values, who writes them and which
are terminal is in [Delivery statuses](#delivery-statuses) below.

**Replay deliveries** — resend what a subscription already matched, selected
by current status, by time frame, or both (`replay` scope, `:8084`, spec §11):

```sh
T=$(./bin/minttoken -owner team-a -scopes replay)

# e.g. everything that dead-lettered, or everything delivered in a window
curl -s -X POST localhost:8084/v1/subscriptions/<id>/replays \
  -H "Authorization: Bearer $T" -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: fix-2026-10-25-1' \
  -d '{"statuses":["dead_lettered"]}'

# → 202 {"replay_id":"55d3ce5d-...","status":"pending","dry_run":false}
curl -s localhost:8084/v1/replays/55d3ce5d-... -H "Authorization: Bearer $T"
# → matched/enqueued/not_replayable + live delivered/failed; "status":"done" when finished
curl -s -X POST localhost:8084/v1/replays/55d3ce5d-.../cancel -H "Authorization: Bearer $T"
curl -s localhost:8084/v1/subscriptions/<id>/replays -H "Authorization: Bearer $T"
```

The selector takes `statuses` (current status: `delivered`, `dead_lettered`,
`dropped`, `failed`, … — the full list is in
[Delivery statuses](#delivery-statuses); `filtered` is rejected with a 400,
because a filtered event never became a delivery), `from`/`to` (RFC3339, by
ingestion time) and `event_refs` — at least one. Time-range and `event_refs`
selectors never pick up `filtered` rows either; `replay.Resolve` excludes them
unconditionally, since a replay re-applies the projection but not the filter.
`"dry_run": true` reports `matched` and `not_replayable` without enqueuing
anything. Replayed events keep their event
reference, are flagged as a replay on the wire (`pubsub-replay-id` header,
`"replay":true` in the SSE payload), travel the normal delivery path (rate
limits, breaker, delivery mode) and must be handled idempotently by the
consumer. Only one job per subscription runs at a time (a second POST answers
409).

### 5. Load test with the harness

```sh
export API=http://localhost:8083        # seed/verify talk to the control plane
./bin/harness seed -owner team-a -types 6 -subs 12 > subs.json
./bin/harness recv  -addr :9090 -out recv.jsonl &
./bin/harness sse   -sub <sse-subscription-id> -owner team-a -out sse.jsonl &
./bin/harness pub   -owner team-a -rate 50 -duration 20s \
  -types harness.type.0,harness.type.1,harness.type.2,harness.type.3,harness.type.4,harness.type.5 \
  -out pub.jsonl
./bin/harness verify -owner team-a -api http://localhost:8083 \
  -events pub.jsonl -received recv.jsonl
```

Notes that cost me time:

- `harness seed`, `verify` and the type resolution of `harness pub` talk to the
  **control plane** (`-api http://localhost:8083`), while `harness pub` itself
  publishes to the **data plane** (`-api`, default `:8080`). Point `-api` at
  whichever the subcommand needs.
- Every subcommand takes its owner from `-owner`; the seeded event types belong
  to `team-a`, so `pub -owner team-a` must match.
- `verify` recomputes the expected deliveries locally — it evaluates the CEL
  filters itself and never asks the platform — and compares them with what the
  receivers recorded and what the status API reports. It exits non-zero on any
  missing or unexpected delivery.

## Deploying to Kubernetes

Two charts, installed in this order because the second one's hook provisions
the platform against the first one's endpoints:

```sh
docker build -t pubsub:dev .                  # or push it and set image.repository

helm upgrade --install pubsub-infra charts/pubsub-infra
kubectl rollout status statefulset/pubsub-infra-postgres   # wait for the stores

helm upgrade --install pubsub charts/pubsub
helm test pubsub                              # reaches /healthz and /readyz in-cluster
```

`pubsub-infra` is one Kafka, one PostgreSQL, one ClickHouse — deliberately
(see `charts/pubsub-infra/values.yaml`); growing them is failover tooling, a
different project from this spike. `pubsub` runs **three replicas of every
service**, which the inbox lease and the groupless presence view make safe,
plus:

- `admin all` as a `pre-install`/`pre-upgrade` hook, so topics, migrations
  and the ClickHouse table exist before the new revision starts serving. Its
  environment is written inline because at `pre-install` the config secret
  does not exist yet.
- `maxUnavailable: 0` rollouts gated by `/readyz` on the three worker
  services, and a `PodDisruptionBudget` per component (`replicas - 1`).
- Readiness is `/healthz` for the five APIs (that is all they expose) and
  `/readyz` for router, dispatcher and status-writer, which fail it when
  their database is unreachable.
- No service account token, no writable root filesystem, no capabilities,
  uid 65532 — nothing here talks to the Kubernetes API.

Configuration is one Secret (`pubsub-config`, or `existingSecret` if you
keep credentials elsewhere) that every pod loads with `envFrom`; keys are
the environment variables of the table above. `HTTP_ADDR` is always set
explicitly because the binaries disagree on their defaults.

Nothing in these charts has been installed on a real cluster yet — they are
`helm lint`-clean and validated against the Kubernetes 1.31 schemas with
`kubeconform -strict`, including the `existingSecret`, `admin.enabled=false`
and single-replica variants.

## Delivery statuses

Every transition of a delivery is one append-only row in ClickHouse
(`delivery_status`, §9); a delivery's *current* status is the newest row for
its ID, the older rows stay as the history. "Newest" is a three-part key —
`(ts, attempt, lifecycle rank)` — not `ts` alone: transitions are produced in
batches (the dispatcher flushes at most every 50 ms), so `in_flight` and
`delivered` of one delivery routinely share a millisecond, and ordering by
timestamp alone breaks the tie by row order, which reported every delivery as
`in_flight`/`0` instead of `delivered`/`200`. The rank is the position of the
status in the lifecycle table below, so a same-millisecond transition always
loses to the one that follows it in the lifecycle. `attempt` exists to keep
the ordering total when two rows of the same status land on the same
millisecond (a retry).

The status summary counts **distinct deliveries**, not rows: `total` is the
number of distinct deliveries seen in the window and each status counts the
distinct deliveries that were *seen in* that status within the window. A
delivery that transitioned through `pending` → `in_flight` → `delivered` is
therefore counted under all three — the counts may sum to more than `total`.
What never happens is counting one delivery twice *within* one status: a
delivery with a dozen status rows still contributes at most 1 to each bucket,
which is exactly the mistake `total` exists to rule out (it was a plain row
count once, and reported 21 for a batch of 20).

These eleven values are the contract — defined once in `internal/status` and
accepted verbatim by the Status API `?status=` filter, by the replay
selector's `statuses` (except `filtered`, see below) and by the status-summary
counts:

| Status | Meaning | Written by | Terminal |
| --- | --- | --- | --- |
| `pending` | The router created it (in the same Kafka transaction as the delivery, reason `router`), or it is parked in the inbox — the `reason` says why: `circuit_open`, `draining`, `rate_limited`, `queue_full` (dispatcher), `no_connection` (SSE gateway), `replay` (replay worker) | router, dispatcher, SSE gateway, replay worker | – |
| `in_flight` | A webhook delivery attempt is running | dispatcher | – |
| `retrying` | The attempt failed, a later one is scheduled; carries `attempt`, `http_code`, `latency_ms` and a reason (`http_error`, `transport_error`, `http_429`) | dispatcher | – |
| `paused` | The circuit breaker is open (`circuit_open`); the delivery waits for the probe | dispatcher | – |
| `sent` | SSE only: written to the connection but not acknowledged yet | SSE gateway | – |
| `delivered` | Webhook: 2xx received. SSE: the client acknowledged the sequence | dispatcher, SSE gateway | ✓ |
| `dead_lettered` | Retries exhausted (`max_attempts`), or the receiver answered `410 Gone` (`gone`) | dispatcher | ✓ |
| `dropped` | Discarded on purpose: inbox overflow (`backlog_max`), full queue of a live-class delivery (`queue_full`), retries exhausted while live (`max_attempts`), live-class with no connection (`live_class`), unknown subscription (`unknown_subscription`), inbox write failed (`park_failed`) | dispatcher, SSE gateway | ✓ |
| `expired` | `expires_at` passed before the delivery went out | dispatcher, SSE gateway | ✓ |
| `failed` | Reserved by the spec ("failed *or* dead_lettered"); **no emitter writes it in the spike** — exhausted retries become `dead_lettered`, so every filter accepts the value but it never appears in the data | – | ✓ |
| `filtered` | The router's verdict for a subscription that was a *candidate* for the event's type but whose filter rejected it (§6.2): `reason` is `filter_mismatch` (filter said no) or `filter_error` (the CEL could not be evaluated, which counts as a non-match too). **No delivery exists** — the row carries the `delivery_id` that delivery *would* have had (`event_ref/subscription_id`), so it lists and counts like any other row. Extension beyond §9, which only describes the statuses of a delivery | router | ✓ |

`filtered` is the trace for a silent case: before it, a subscription whose
filter matched nothing left **no** record anywhere — no delivery, no status,
not even a log line — so "why did this never arrive" could only be answered by
re-running the filter by hand. Note the deliberate boundary: an event with **no
subscription at all** for its type gets no status (there is no subscription ID
to attach one to); instead the *publish* response carries a `warning` (see
above), because that is the only place the mistake is visible at the source.

Because a `filtered` row is not a delivery, the replay selector rejects
`"statuses":["filtered"]` with a 400 (`status "filtered" cannot be replayed:
the filter rejected this event, so no delivery ever existed for it`) — a replay
re-applies the projection but **not** the filter, so replaying one would
deliver exactly what the filter said no to. Time-range and `event_refs`
selectors exclude these rows too, unconditionally, in `replay.Resolve`.

`filtered` rows *are* counted in `status-summary` (in their own bucket and in
`total`, which is the number of distinct delivery IDs seen in the window): a
subscription whose filter rejected every event reports `total` equal to the
number of rejected events, all of it under `counts.filtered` — which is the
point of the row.

The record also carries `reason`, `attempt`, `http_code`, `latency_ms`,
`connection_id`, the replay ID and the event's retention class — never a
payload (§9). Statuses lag the real world by 1–5 s because `status-writer`
batch-inserts them. An unknown `?status=` value on the Status API is not
validated: it simply matches no rows (the replay selector rejects the same
mistake with a 400).

Replay *jobs* are a different, unrelated state machine in `replay_jobs`:
`pending → running → done`, plus `cancel_requested → cancelled` on a cancel
and `failed` on an error.

## Circuit breaker and dead letters

Two independent mechanisms that both deal with a failing receiver. The
**circuit breaker** decides *whether to attempt at all* — a gate on the
endpoint. The **dead letter** is the verdict *after* attempting and giving up
— a terminal status on one delivery. The breaker never dead-letters anything,
and a dead letter never trips the breaker.

### The breaker: a traffic light per subscription

State machine of `internal/dispatch/breaker.go`, in memory and per
subscription (it resets on a dispatcher restart: one bounded storm of a dead
endpoint per restart is the documented cost):

```
CLOSED ──(5 consecutive failures)──► OPEN ──(probe interval elapsed)──► HALF-OPEN
   ▲                                  ▲                                  │
   └────(probe answers 2xx or 410)────┴──────(probe fails: re-open)──────┘
```

- **Failure**: 5xx, any other 4xx, connection refused, timeout, DNS error.
- **Success**: 2xx **and 410** — the receiver answered, so it is healthy.
- **Neither**: `429` pauses the subscription for `Retry-After`, consumes no
  attempt and counts no failure (spec §6.4).
- Defaults: `cb_failure_threshold=5` **consecutive** failures (any success
  resets the counter), `probe_interval_s=300`, clamped to 5–15 minutes.
- A failed probe re-opens for the **full** interval, so an endpoint that stays
  down costs exactly **one request per probe interval** — the open/close loop
  is bounded by design, never a storm.

What each state actually does:

| State | New delivery from Kafka | Parked row (drain) | HTTP sent |
| --- | --- | --- | --- |
| `closed` | attempted: `in_flight` → `delivered` / `retrying` / `dead_lettered` | drained at `drain_rate_per_s` | yes |
| `half-open` | the first one becomes the probe, every other is refused and parks (live class retries in memory) | the first row is the probe, the rest wait | exactly 1 |
| `open` | refused: `paused (circuit_open)` → inbox → `pending (circuit_open)` | skipped — except at probe time, when the first row *is* the probe | none |

Two rules follow: *open means don't try* (protect the receiver from us) and
*park means don't lose* (the delivery waits in PostgreSQL, bounded by
`backlog_max`, beyond which `dropped` appears — the spec's
guaranteed-delivery-vs-storage trade-off, §16). The drain runs through its own
token bucket and is gated by the breaker, and while a drain batch runs new
non-live deliveries park (`reason=draining`), so drain and live traffic never
overlap on one subscription.

**Live-class deliveries (§12) are the exception**: no inbox duty, so while the
breaker is open they retry in memory with backoff and end as `dropped
(max_attempts)` — never parked, never dead-lettered.

### The dead letter: a delivery that ran out of chances

`dead_lettered` is a terminal status, **not a queue**: there is no DLQ table
and no DLQ topic, only the ClickHouse row that says "finished,
unsuccessfully". Two ways in:

| Door | Trigger | Cost |
| --- | --- | --- |
| `gone` | the receiver answered **410 Gone** | one attempt — the receiver's own decision (see below) |
| `max_attempts` | all `DISPATCHER_MAX_ATTEMPTS` (10) attempts failed | ten attempts with exponential backoff (0.5 s → 60 s, jittered) |

After either door: no retry, no parking, no breaker involvement, ever. The
only way back is a **replay** (`{"statuses":["dead_lettered"]}`), which
re-emits `pending` for the same delivery ID and runs the whole lifecycle
again — that is this spike's DLQ.

**Why a receiver would answer 410**: HTTP's permanent "gone", used as an
opt-out — tenant deleted, endpoint decommissioned, subscription cancelled
downstream. It turns "keep hammering a receiver that told you to stop" into
one clean decision: no retry budget burned, no breaker noise (it counts as a
*success*), and a status the replay API selects on. It is a spike extension:
§9 only defines `failed or dead_lettered = retries exhausted`.

### How they interact (barely)

| Situation | The breaker does | The dead letter does |
| --- | --- | --- |
| Receiver totally down | opens after 5 failures, everything parks | almost nothing arrives here — attempt 6 is already refused |
| Receiver alive, one payload keeps failing | never opens (successes reset the counter) | `dead_lettered (max_attempts)` on attempt 10 |
| Receiver answers 410 | counts as success, stays closed | `dead_lettered (gone)` at once |
| Breaker open | emits `paused`, delivery parks | irrelevant — no attempt is made |
| Already `dead_lettered` | never sees it again | terminal until a replay |

The two answer different questions: the breaker detects *"the endpoint is
broken"* (stop trying, park, wait for recovery), the dead letter detects *"the
endpoint is fine but this delivery won't make it"* (give up, make it
replayable).

### Timeline: receiver hard down

```
events 1-5    in_flight → retrying (transport_error), backoff 0.5s 1s 2s 4s
              5th consecutive failure → breaker OPEN
events 6-∞    paused (circuit_open) → pending (circuit_open)   no HTTP at all
t+300s        drain: row 1 is the probe → refused → re-OPEN     one request
              row 2: allow() is false → paused → row stays parked
...           one request per probe interval until the receiver returns
probe 200     breaker CLOSED (failures=0) → rows drain at drain_rate_per_s
              every parked delivery ends delivered
```

With an *intermittently* failing receiver the breaker never opens, and one
unlucky delivery instead reaches `dead_lettered (max_attempts)`.

Breaker cycles add status rows every time (`paused`, `pending`, `retrying`) —
`delivery_status` is append-only — but they never produce new deliveries or

## Where the spike stands

A full harness run verifies with zero missing, zero unexpected and zero
duplicate deliveries across both channels and all three delivery modes, with
attribute filters, data filters and projections — at 50 events/s (p50 22 ms /
p99 28 ms) and at the 1,000 events/s N1 target (see the next section).
Fault injection on the dispatcher is covered too (circuit breaker with
receiver outage, hard kill and restart, restart with a parked backlog), and so
is the SSE gateway's restart path — graceful SIGTERM and hard SIGKILL with a
live client — every scenario ending with zero loss and zero duplicates
client-side. The `Last-Event-ID` backlog fetch is implemented and tested: a
client reconnected by cursor after its gateway was SIGKILLed received all
1,200 events (100 through the cursor path), `missing=0, duplicates=0`, and a
cursor reconnect after a client-side kill recovered a 119-row parked backlog
instantly. The replay API (spec §11) is built and tested end to end: 30
dead-lettered events replayed to 30 delivered, a time-frame replay of 20,
dry-run, idempotency, cancel-at-batch-boundary and the not_replayable paths —
full results in
[docs/deviations-and-open-points.md](docs/deviations-and-open-points.md).
Not exercised yet: the soak test, restart-mid-job recovery of the replay
worker, the multi-day offline scenario and multi-node SSE gateway failover.

## Load test at 1,000 events/s (spec 15.2, targets N1/N3)

Measured on the local compose stack on one 8-core laptop: single-node
Kafka/PostgreSQL/ClickHouse and one instance of every service.

Topology: `team-b`, 4 event types (`load.type.0..3`), 40 subscriptions — 20
webhook and 20 SSE — covering unordered, per-shard ordered (attribute filter),
key-ordered (data filter `int(data.seq) % 2 == 0`) and rate-limited webhook
subscriptions, plus 20 connected SSE clients. 1 KiB JSON payloads, batch mode
(100 events per request).

```sh
./bin/harness seed -owner team-b -prefix load -types 4 -subs 40 > seed-b.json
./bin/harness recv -addr :9090 -out recv.jsonl &
# one per seeded sse subscription
./bin/harness sse -sub <id> -owner team-b -addr http://localhost:8082 \
  -out sse-<id>.jsonl -duration 240s &
./bin/harness pub -owner team-b -rate 1000 -duration 30s \
  -types load.type.0,load.type.1,load.type.2,load.type.3 \
  -payload 1024 -out pub.jsonl
./bin/harness verify -owner team-b -api http://localhost:8083 \
  -status-api http://localhost:8081 -events pub.jsonl -received recv.jsonl
```

Result: 30,000 events published at a sustained 1,003 ev/s with zero publish
failures, fanning out to ~146,000 deliveries. The dispatcher burst to ~3,100
webhook deliveries/s and drained to `queue_depth=0` with zero retries, parks,
drops or dead-letters. Latency from publish to receipt:

| Channel | p50 | p90 | p99 | p99.9 | max |
| --- | --- | --- | --- | --- | --- |
| Webhook (unlimited subs) | 32 ms | 39 ms | **51 ms** | – | 109 ms |
| SSE | 51 ms | 65 ms | **88 ms** | 140 ms | 153 ms |

N3 (p99 < 1 s, target a few hundred ms) is met with margin on both channels.
Rate-limited webhook subscriptions (`rate_limit_per_s`) show minutes of tail
latency by design: they drain their backlog at the configured rate. The oracle
agrees: `expected=145918 missing=0 unexpected=0 duplicates=0` over all 40
subscriptions.

Caveats: this validates the pipeline shape and per-stage latencies, not
cluster-scale HA (single broker, single node of everything). ClickHouse status
write/query throughput is the most pressured component at this rate. The
status table is cumulative, so re-running a load test for the same owner
counts earlier runs' deliveries too — the harness scopes Status API queries to
the run's publish window (`from`/`to`), keep that in mind when probing the API
by hand.

The run found and fixed two real bugs, worth remembering when touching these
paths:

- The SSE delivery stage produced to `sse-live` with one synchronous Kafka
  round trip per record inside the serial batch loop, capping the fan-out at
  ~1,260/s (SSE p50 was 4.7 s). Now one produce per poll batch
  (`produceLiveBatch` in `internal/sse/delivery.go`); franz-go keeps
  per-subscription order because same-partition records are serialised in
  produce order.
- The status API's keyset cursor was bound as a `time.Time`, which the
  ClickHouse driver rendered as `toDateTime('...')` at second precision. With
  100+ status rows in one second — only under load — the page repeated forever
  and pagination stalled, hiding real deliveries from `verify`. Cursor and
  `from`/`to` are now bound as millisecond-precision strings inside
  `toDateTime64(?, 3)` (`internal/chquery/chquery.go`).

## Deviations from the spec, on purpose

Tracked, with reasons, in
[docs/deviations-and-open-points.md](docs/deviations-and-open-points.md)
together with the spec's open decisions and what this spike did or did not
answer. Short version: registry reads PostgreSQL (poll plus a `NOTIFY`
trigger) instead of a compacted config topic, inbox rows are deleted in
batches instead of by watermark, HS256 dev auth instead of JWKS, the replay
selector rejects `event_types` (status records carry no event type) instead
of implementing it, and SSE multi-node routing uses presence with a node ID
rather than rendezvous hashing.
