**Eventarium** is an event-delivery platform: CloudEvents go in over REST, and
each subscriber gets the events it asked for — filtered, projected, delivered
over webhooks or Server-Sent Events, with every delivery tracked to a terminal
outcome and nothing lost when something breaks.

It is a working end-to-end implementation of the
[specification](spec.md): eight services on Kafka, PostgreSQL and
ClickHouse, exercised by a load-test harness with an independent oracle
rather than by assertion alone.

```text
publish-api ─► Kafka events-<class> ─► router ─► Kafka deliveries ─┬─► dispatcher ─► webhook URLs
     ▲                                              │               └─► sse-gateway ─► SSE clients
     │ control plane (registry-api → PostgreSQL)    │
     └──────────────────────────────────────────────┴─► Kafka delivery-status ─► status-writer ─► ClickHouse ─► status-api
                                     overflow/offline ─► inbox (PostgreSQL) ─► drained back to the hot path
```

### Filtering and projection per subscription

Each subscription carries its own CEL filter over the event's attributes and
data, an optional allowlist projection, and an optional ordering key. Two
subscribers of the same event type see the same event arrive as two different
payloads — one narrowed to the fields it asked for, one filtered out entirely
and recorded as such.

```text
attributes["region"] == "eu" && data.total > 100   # attribute + data filter
projection: ["order_id", "total"]                  # the subscriber never sees "internal"
ordering_key: json:<dotted.path>                   # stable per-key ordering
```

### Two delivery channels, one status model

**Webhooks** — POST with `ce-*` attributes, delivery metadata in `pubsub-*`
headers, optional HMAC signature, SSRF guard, per-endpoint rate limiting.

**SSE** — streaming connections with heartbeats, explicit acks, and cursor
reconnect: a client that echoes back its last `id` gets everything it missed
replayed from the topic, merged with the live stream and deduplicated.

Both write into the same append-only status store, so "what happened to this
delivery" is answerable for either channel.

### Guaranteed, tracked delivery

Every delivery carries a status through `pending → in_flight → delivered`,
with eleven statuses in total covering retries, pauses, drops, expiry and
dead letters. Delivery is at-least-once: an aborted transaction or a crashed
consumer means the batch is re-consumed, which shows up as duplicates rather
than loss.

Nothing is dropped silently. A parked delivery sits in PostgreSQL until a
receiver recovers; a delivery that exhausts its retries becomes a
`dead_lettered` row that a [replay](api.md#replay-deliveries) can resurrect.

### Failure handling that protects the receiver

A per-subscription [circuit breaker](reliability.md#the-breaker-a-traffic-light-per-subscription)
opens after five consecutive failures and then costs a failing endpoint **one
request per probe interval** — never a storm. Deliveries that arrive while it
is open park rather than fail. `429` honours `Retry-After` without consuming
attempt budget; `410 Gone` is a clean, permanent opt-out.

### Transactional where it counts

A publish batch is written in one Kafka transaction, so a batch that fails
half-way is not partially accepted. The router wraps each poll batch —
deliveries, pending statuses and the consumed offset commit — in a single
transaction, which is what makes the fan-out exactly-once-from-the-consumer's-
point-of-view despite at-least-once underneath.

### Horizontally scalable

Every component runs with any number of replicas. Kafka partitions do the
work-splitting for consumers; the two pieces of work that are *not*
partition-scoped are handled explicitly — the dispatcher's inbox duty runs
under a PostgreSQL advisory-lock lease (exactly one drainer in the fleet), and
the gateway's presence view consumes groupless so every node sees every node's
connections.

### Observability you can query

Per-stage latency travels in record headers. Every status transition lands in
ClickHouse, queryable by owner, subscription, status and time window, with a
summary endpoint that counts distinct deliveries rather than rows.

## Measured, not asserted

The numbers below come from the harness's independent oracle, which
recomputes expected deliveries locally — evaluating the CEL filters itself,
never asking the platform — and compares them against what receivers actually
recorded. Full results in [Performance](performance.md).

| What | Result |
| --- | --- |
| Throughput | **1,003 ev/s** sustained, 30,000 events fanning out to 145,918 deliveries |
| Loss | **`missing=0 unexpected=0`** at every rate and under every injected fault |
| Webhook latency | p50 **34 ms**, p99 **59 ms** at 1,000 ev/s |
| SSE latency | p50 **56 ms**, p99 **90 ms** at 1,000 ev/s |
| Chaos (9 replicas, one fault mid-publish) | `kill -9` of a dispatcher, router **and** gateway: **0 lost** |
| | PostgreSQL down *and* receiver offline, overlapping: **0 lost** |
| | ClickHouse down 20 s: **0 lost** · Kafka broker restart: **0 lost** |
| Crash failover | a killed dispatcher's partitions are owned again in **13 s** |
